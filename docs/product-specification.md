# Product specification, version 1

The host assistant drafts a messaging architecture, supplies explicit structured facts, and explains the review. The plugin contributes bounded decisions, reproducible arithmetic, relevant evidence and failure-injection tests. There is no universally perfect architecture.

| Check | Positive proposition | Necessary facts |
|---|---|---|
| Retry safety | Required business effects cannot repeat because of retries or redelivery. | Effect semantics; stable identity; enforced uniqueness; atomicity; retry and deduplication lifetimes; external effects. |
| Acknowledgement durability | Acknowledged operations meet the declared failure-survival requirement. | Exact acknowledgement boundary; durable commit timing; exhaustive failure-survival guarantee. |
| Queue overload | Overload controls meet the declared queue-bound and accepted-message preservation requirements. | Queue limit; admission timing; loss policy; retry backoff. |

Verdicts are supported, contradicted and insufficient_information. Supported is conditional on the supplied facts and the specified failure model. Missing mechanisms are unknown, not assumed absent. An explicitly absent mechanism can contradict a requirement when a concrete violating effect is established.

The queue check establishes whether overload controls are specified; it does not establish a latency SLO. Benchmark evidence and latency results are returned separately. The durability check does not verify real deployment placement; fault-injection tests are required. A duplicate-safe database write does not automatically protect external effects.

## Interfaces

MCP: `review_architecture(requirements, design, workload, deployment)`.
HTTP: authenticated `POST /v1/reviews` with the identical JSON input.
CLI: `arch-review review INPUT.json` with the identical output structure.

The schema is defined by the Pydantic models and generated by `arch-review schema`. Additional properties and non-finite numeric values are rejected. Inputs are capped at 100 KB. Unknown fields remain null/omitted. A single architecture review may have supported and contradicted checks simultaneously; there is no misleading aggregate approval.

Output distinguishes review completion, rule verdict, model verdict, model calibration status, source provenance, missing information and production-risk consequences. Missing model inference means partial completion even when deterministic rules can answer.

## Model and evidence

One local Laya checkpoint, three typed choice questions, context limited to 1024 tokens with a 256-token head budget. Relevant source lessons are compacted; essential design facts are not silently dropped. A context overflow invalidates the model answer. Full case studies stay in the evidence library.

The first evidence release spans messaging, social feeds, media delivery, commerce, payments, search, analytics and multi-tenancy. V1 automated judgments remain messaging-specific. Public sources describe dated subsystems, not complete current private company architectures.

## Release conditions

Software checks must pass. Model quality requires expert-reviewed independent cases, comparison against the base checkpoint and a general AI, missing-information and contradiction recall, calibration assessment, and a blind backend-engineer pilot. The bundled data has no expert-reviewed labels yet. Passing software tests does not satisfy these conditions.
